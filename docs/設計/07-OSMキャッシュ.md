# OSM 取得結果キャッシュの設計

Overpass API の応答をサーバ側でディスクにキャッシュする仕組み。
Issue #60 / PR #61 で実装（2026-09-18）。

## なぜサーバ側に置くか

ブラウザから直接 Overpass API を叩くと、公開インスタンスにリクエストが集中する。
サーバが一度取得して共有する形に組み替えた。

## 配置

`app/src/lib/osm/` にサーバ側プロキシとディスクキャッシュを実装。

## クエリの範囲

**`way["highway"](bbox)` に限定する。** タグ指定なしの `way(bbox)` だと、
建物や境界など**経路探索に使わない way まで取得してしまう**。
探索結果に影響しないものを取得しないことが狙いです。

応答サイズも減りますが、これは副次的な効果です。

リクエスト時に `wayHighwayExcludes` で highway 種別フィルタをかけるので、
取得側は highway タグに絞った広めにとって構いません。

## タイル分割と取得手順

1. タイルを 1/64°（0.015625）単位に分割する
2. 欠けているタイルだけまとめて union クエリで取得する
3. タイル単位で trim して保存する
4. 必要なタイルを merge する
5. 最後に一度 trim する

境界を跨ぐタイルは union でまとめて取ることで、1 回のクエリで済ませる。

## 取得量と時間の上限

`app/src/lib/osm/limits.ts` に 2 つの上限を持つ。

| 定数 | 既定 | 内容 |
|---|---|---|
| `MAX_OSM_CELLS` | 512 | 1 回の取得で扱うセル (1/64° 格子) 数の上限 |
| `OSM_FETCH_BUDGET_MS` | 40000 | Overpass の fetch にかける時間の上限 [ms] |

`MAX_OSM_CELLS` の 512 は 23×23 格子で、37°N ではおよそ 40km×32km に相当する。
`OSM_FETCH_BUDGET_MS` の 40 秒は、サーバ側の `[timeout:30]` に部分応答の転送ぶん 10 秒を足した値になる。
どちらも仮の値で、`log_lines` の requested / fetch と取得要素数の実測で見直す。

セル数が上限を超えるときは Overpass を叩かず、キャッシュ済みの分だけで続行する。
時間予算で切れたときも同じくキャッシュ済みの分で続行する。
予算は header と本文 (`res.json()`) の両方に効く。
本文の受信中に切れると `remark` 判定ではなく時間切れとして扱い、キャッシュ済みで続行する。
このとき取得できなかったセルはキャッシュに載らないので、次の取得で改めて対象になる。
呼び出し元は戻り値の `partial` と `reason` で取り切れなかったことを知る。
`/api/path-find` は応答の `osmPartial` に載せ、`/api/preload-osm` は応答の `partial` に載せる。
定期更新も 1 回に処理する失効セルを `MAX_OSM_CELLS` 枚までにし、残りは次回に回す。

## 端点先読み

経路探索は OSM の取得を含むため、p95 で 3 秒・最大 15 秒ほどかかる。
始点・終点を設定してから検索が走るまでにギャップがあるので、その間に範囲を温める。

- クライアントは端点が変わるたびに `/api/preload-osm` を出す。
- 範囲は経路探索と同じ `getBoundaryBox(begin, end)` にする。
- 片方だけのときは `getBoundaryBox(p, p)` でその端点の周辺だけを温める。
- 端点は連続で変わりうるので 400ms デバウンスする。
- 検索は先読みを待たない。検索開始時に未実行の先読みは捨てる。
- 閲覧中の pan/zoom では先読みを出さない。
- 先読みと経路探索が重なったときは `requireOSMData` が同じ範囲の fetch を 1 回にまとめる。

## 同時取得とレート制限

`preload-osm` と `path-find` は別リクエストだが同一プロセスで動く。
`requireOSMData` は同じ boundaries への in-flight の fetch を 1 つにまとめる (`index.ts` の `inFlightFetches`)。
無効キャッシュのセルが同じなら、まとめのキー (`simplifyBoundaries` の出力) が一致し、Overpass は 1 回だけ叩かれる。
まとめた結果は両方の呼び出しがそれぞれキャッシュへ書く (同じ内容を書くだけなので壊れない)。

- まとめはプロセス内のメモリで持つ。複数プロセスに分けると Overpass はプロセスごとに 1 回になる。
- 同一範囲の同時 fetch が 1 回になることは `tests/osm-cache/index.test.ts` で検証している。
- Overpass への同時接続数の上限は設けていない。範囲が異なる取得はそれぞれ独立に走る。
- 429 や 504 は `fetchOverpassData` が throw する。経路探索は 500 を返し、リトライや待機はしない。
- 端点先読みは 400ms デバウンスと検索開始時の cancel で、連続した取得を抑える。


## TTL / eviction / versioning は意図的に未実装

固定エリアで緩やかに OSM が更新される前提では実害が出にくいため、実装していない。

**見直しトリガ:**

- 対応エリアを大幅に拡大する
- 最新 OSM の反映が必要になった
- クエリの意味が変わる

リセットは `OSM_CACHE_DIR` を消せばよい。
