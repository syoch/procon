# bench 測定と比較

## 概要

1 回の経路探索にかかる CPU を測定項目ごとに測り、base と head の 2 回の計測を
比較して計算量の回帰を検出する仕組み。
計測ハーネスは `app/bench/` に置いた。

- 同じランナー上で base と head を 2 回測って比べる。差分はそのまま PR の変更によるものとして読む
- 比較の単位は測定項目 ID だけ。ハーネスの同一性は求めない
- 校正（`lib/reference.ts`）を前置して、ランナーの負荷の変化と「本当に遅くなった」を区別する
- 判定は終了コード 3 通り（0 / 1 / 2）で表す

使い方と測定項目の読み方は [`app/bench/README.md`](../../app/bench/README.md) に書いてある。
この文書は「なぜその方式にしたか」だけを書く。

## 同一性ゲートを廃止した

### 最初に採用した方式

最初に採ったのは「base と head の `bench/` が同一でなければならない」というゲートだった。
`diff -rq` でハーネスを比べ、差があれば `harness_drift` として比較をスキップする方式。

### 破綻した理由

`app/bench/` は `app/src/` の実装モジュールを直接 import している（11 箇所）。
そのため `app/src` のモジュールを移動すると、bench の import パスも追随して bench の中身が変わる。

実例として `src/lib/requestContext.ts` を `src/lib/tracing/requestContext.ts` に動かしただけで
同一性ゲートは drift と判定し、性能比較をスキップした。
性能的には完全に中立な変更である。

### 現在の方式

比較の単位を**測定項目 ID** に置き、base は常に自分の bench で自分の `app/src` を測る。
base の bench が head の bench と違っても、同じ ID の測定項目同士は比較できる。

```
App@base    <-> bench/Measure@base   ->  bench 結果 ---+
                「同一でなくても良い」                  +-> 比較@HEAD -> CI の可否 / Summary
App@HEAD   <-> bench/Measure@HEAD   ->  bench 結果 ---+
```

これで `app/src` のモジュール移動が自由になる。
移動すると bench の import パスも追随して bench の内容が変わるが、測定項目が同じなら比較は成立する。

## 測定項目 ID を一元管理しない

測定項目 ID は `{シナリオ}[/{モード}]/{段}` の文字列で、型でも実行時の検証でも絞らない。
ID の組み立ては `run.ts` の `stageId()` だけの 1 箇所に置く。

モードを使うシナリオはモードごとに 1 個作る（`pipelineScenario(mode)`）。
モードを使うかどうかは `Scenario.modes` の有無で分かるので、
「どのシナリオがモードを使うか」を表す表は持たない。

### 理由

ID を一元管理する表（段の一覧と「モードを使うか」の対応）を置くと、
シナリオを 1 つ追加するたびに、その 2 つを両方直す必要が増えて破綻する。
段の追加とモードの有無が同時に増えるので、整合を保つ手間も増える。

**型の保証より、壊れたときに静かに誤った比較をしないことのほうが重い。**
段の名前は文字列なので typo をコンパイルで弾けない。
その代わり、段の名前を変えると測定項目 ID が変わり、
base と head で共通する項目が「削除 + 追加」になる。
つまり typo は差分に出たときに読む。比較時に静かに「比較できない項目」になるのではなく、
追加・削除として明示される。

受け入れた損失:

- typo の検出は差分に任せる（コンパイルでは弾けない）
- 「レジストリに無い段を測ったときのエラー」と「レジストリにある段を測り忘れたときのエラー」は無い

`app/bench/ids.ts` はこの判断で削除した。

## base と head で共有する契約

base の JSON は base の版が作ったものなので、構造は base の版次第である。
構造を共有すると drift が再発するため、共有する契約は次の 2 つだけに絞る。

| 共有するもの | 形式 |
|---|---|
| 測定項目 ID | `{シナリオ}[/{モード}]/{段}` |
| 測定値 | `median`（中央値、ms） |

共有しないもの:

- 結果 JSON の構造（`measurements` がどの階層で持つがあるか、`total` があるかどうか）
- シナリオの実装、`StageRecorder` などの計測インフラ
- 測定条件（`mode` / `iterations` / `warmup` / `node` / データ規模）

測定条件は ID に入れない。
ID に入れるのは**上流から渡せず、リビジョンによって変動しうる値だけ**にする。

| 値 | 扱い |
|---|---|
| `{シナリオ}` | ID の 1 番目の成分 |
| `{モード}` | モードを使うシナリオの ID の 2 番目の成分 |
| `{段}` | ID の最後の成分 |
| `iterations` / `warmup` | CLI で渡す。CI は `deploy.yml` の 1 箇所で base と head に同じ値を渡す |
| `node` | `node-version` で CI が固定 |
| データ規模（ノード数・辺数・経路長） | 同じ bbox の OSM キャッシュが保証する |

### 再帰走査を持たない

`report.measurements` をそのまま読んで突合する。
base の JSON が別の階層でも比較できるようにする再帰走査（`extractMeasurements`）は持たない。
構造を固定して、base と head で同じ形であることを前提にする。

出力の構造は `lib/report.ts` の zod スキーマが契約として持つ。
版の違う JSON には測定項目 ID が入っていないので exit 2、
版が同じで構造が契約を守らないものは契約違反として exit 1 にする。

## 比較結果の分類

測定項目 ID 単位で突き合わせた結果は 3 つに分かれる。

| 分類 | 条件 | 回帰判定 | 表示 |
|---|---|---|---|
| 共通 | base と head の両方に同じ ID がある | 入る（`median` の比を見る） | 表に比が出る |
| 追加 | head にだけ ID がある | 入らない | 表に「追加」として出す |
| 削除 | base にだけ ID がある | 入らない | 表に「削除」として出す |

追加と削除は「測定対象が変わった」ことを意味するので、回帰判定には入らない。
ただし必ず表示する。
黙って比較から外すと、何が変わったか読めない。

ID をリネームすると削除 + 追加になるため、比較されない。
これは「測定対象を変えた」のと同じ扱いになる。

### 回帰判定に入る共通 ID の線引き

共通 ID でも、絶対時間がノイズ床（`--min-ms`、既定 0.5ms）を下回る項目は判定から外す。
0.02ms の項目が 0.04ms になってもそれは測定解像度の話で、性能の回帰ではないため。

回帰の判定は `head.median / base.median` が許容倍率（`--tolerance`、既定 1.5）を超えたときに出る。

## 共通 ID が 0 件のときに exit 2 する

両側に共通する測定項目 ID が 1 つも無いときは比較不成立として exit 2 にする。

共通 ID が 0 件のときは、比べる対象が無いので回帰の判定も出せない。
ここで exit 0（緑）にしてしまうと、
「比較できて回帰なし」と「比較対象が無かったため判定していない」が区別できなくなる。

**暗黙の緑を作らない**ための判定であり、性能の悪化を意味しない。

同じ理由で、結果 JSON の版が違うとき（測定項目 ID を持つ出力ではない）も exit 2 にする。

## 校正は測定項目 ID を持たない

校正（`app/bench/lib/reference.ts`）は、アプリのコードに一切依存しない固定仕事量の整数演算を
base と head の計測の直前に 1 回ずつ測る。使う仕事量は常に同じなので、
所要時間だけが機械の速度を反映する。

**校正は測定項目 ID を持たない。**
理由は目的が違うため。

- 測定項目は「アプリのどこがどれだけ遅い」を測る
- 校正は「2 回の計測の間でランナーの状態がどう変わった」を測る

アプリが速くなったときの差分を検出するのが測定項目の目的で、
校正をそれに乗せると目的が混ざる。
校正は別の判定枠で独立に判定する。

### 校正が使う仕事の性質

校正に使う仕事は次の性質を満たす必要がある。
どれか 1 つ崩れると、測る物が「機械の速度」でなくなる。

- 整数演算だけを使う。浮動小数点の演算と除算は実行時間が一定にならず、実装が違えば速さも変わる。`Math` も実装ごとに速さが違うので使わない
- 少量の固定長テーブル以外は確保しない。大きなオブジェクトの確保を混ぜると、校正ではなくゴミ集めの話を測ることになる
- 分岐は事実上取られないものだけ置く。データによって予測が外れると、実行時間が揺れて数パーセントの判定も壊れる
- 仕事量を時間から逆算しない。逆算すると遅い機械ほど仕事量が減って常に同じ時間になり、比較そのものが消える
- 戻り値を必ず外へ出す。捨てるだけだと最適化で丸ごと消される

### 校正ゲートは実行順に依存していた（2026-10-04 に判明）

**校正ゲートは base と head の実行順に依存していた。**
先に走ったジョブがランナーのコールドコストをすべて吸収するため、
校正の比が「どちらが先に走ったか」だけで決まっていた。

#### 実測（PR #105 の bench ジョブ）

| | median | min | max |
|---|---|---|---|
| base 校正 | 99.47ms | 97.09ms | 139.25ms |
| head 校正 | 193.78ms | 193.43ms | 194.64ms |

比は 1.95x で許容（±0.1）を大きく超え、`校正で機械の速度が変わった可能性` として exit 2 になっていた。
この実行では**回帰判定が 1 度も行われていなかった**。

別の PR のログ（bench job 111355991136）では、1 ジョブ内の推移がこうなっている。

| 測定位置 | base ジョブ | head ジョブ |
|---|---|---|
| 先頭の aggregate calibration | 179.09ms | 89.91ms |
| 直後の `pipeline` の直前 | 89.91ms | 90.09ms |
| `split` の直前 | 57.37ms | 57.35ms |
| `cache-read` の直前 | 57.35ms | 57.35ms |

base ジョブの**先頭だけ** 179ms で、あとは 57 から 90ms に落ち着いている。
1 ジョブ内の 3 倍の落差が、計測順バイアスの直接証拠である。
シナリオ単位の校正は 1.00x で揃っているのに、先頭の aggregate だけが外れる。

PR #108（main ベース。exit 2 の修正が無い）では
1 回目が 1.73x で fail、2 回目が 0.50x で fail、3 回目が pass だった。
**逆向きに外れている**のがポイントで、どちらが先に計測された側かだけで結果が決まっていた。

#### 採用した方法

**プロセス内で最初の校正だけ、先頭の 1 回を捨ててから 5 回測り直す**（`lib/reference.ts`）。

- プロセス内で最初の 1 回だけはランナーのコールドコスト（全速になるまでの時間、
  ページキャッシュの読み込み、Turbo の立ち上がり）をすべて含む
- それを採用すると base と head の校正が実行順でずれるので、捨てる
- 捨てたあとの 5 回をまとめて中央値にする。1 回だけ測るより外れ値に強い
- 2 回目以降の校正（シナリオ直前）は 1 回だけで測る。その時点までは既に十分動いている

#### tradeoff

集めるのは「機械の速度」であって「最初は何も動いていない状態」ではない。
そのため**計測開始時の機械の状態は校正からは読み取れなくなる**。

「ランナーがコールドスタート状態だった」ことが分かる情報は失う。
その状態では比較そのものが成立しないので、使わないほうがよい。

#### 不採用にした案

| 案 | 不採用の理由 |
|---|---|
| D. 順序を反転させる（head を先に測る） | バイアスを別の走者に移すだけで構造は直らない。1.95x と 0.50x が逆向きに出ていることがその証拠である |
| E. 許容を緩める（1.5x くらいまで） | 校正が外れているときに回帰判定を黙って止めることになる。「偽陽性でも緑にしない」という方針に反する |
| B 単独（複数回取って中央値だけ） | コールドコストは数回続くため、先頭の値を採用するままだと外れる。捨てる回と組み合わせる必要がある |
| C（シナリオ単位の校正で判定する） | 各シナリオ直前の校正は既に 1.00x で揃っているので検出には効くが、aggregate の情報が完全に失われる。捨てたあとの数値は使えるので、捨てる必要がない |

## 退避した比較の線引き

以下は比較しない。
判断の根拠とともに示す。

- 測定条件の比較: 測定条件を ID に入れない方針により、同じ ID の項目どうしは同じ測定対象を指すので条件を比べる必要がない
- データ規模の比較: 同じ bbox の OSM キャッシュが同一グラフを保証するので比較対象から外す
- 校正マップ（`scenarioCalibration`）を持たないシナリオの校正: 比較対象の測定項目が無いので、そのシナリオの校正も突き合わせない

## fixture の動的取得

フィクスチャは git に持たない。`app/bench/scripts/fetch-fixture.ts` が
`OSM_CACHE_DIR` に本番と同じセルファイル形式で書き出す。

### セルファイルだけを持つ

フィクスチャはセルファイルだけで表現する。
manifest（`meta.json`）は置かない。

- 領域はセルファイル名の範囲から求める
- 規模（セル数・ノード数・way 数）はセルの中身から数える
- 取得時刻は最も新しいセルファイルの更新日時から求める

セルファイル名が領域を表し、規模もセルから数えられるので manifest は不要だと判断した。

### 取得は requireOSMData に任せる

セルへの分割・問い合わせ・保存はすべて本番と同じ経路にする。
`scripts/fetch-fixture.ts` は `requireOSMData` を 1 回呼ぶだけにした。

`requireOSMData` は取得済みセルを `readCache` で飛ばし、
残りを `simplifyBoundaries` で 1 クエリにまとめる。
したがって 1 回の実行で投げるクエリは 1 本だけで、レート制限に掛かる回数を増やさない。

**セル単位に問い合わせる実装は採らない。**
1 クエリを 8 本に分割すると、レート制限に掛かる回数だけが増える。

### 504 への対処は再試行

公開 Overpass は混雑すると 504 を返す。
実体は 2 種類あり、どちらも同じ HTTP 504 で返る。

| 実体 | 意味 |
|---|---|
| `Dispatcher_Client::request_read_and_idx::timeout` | サーバが混んでいる |
| `Dispatcher_Client::request_read_and_idx::rate_limited` | IP 単位のレート制限。連打すると当たる |

`fetch-fixture` は失敗時に全体を取り直す。
3 回まで試して、5 秒置く。
取得済みセルはキャッシュに残るので 2 回目以降のクエリは減る。

全セルが揃っていれば何もしない（no-op）。

### 領域

長岡市中心の bbox をセル境界にスナップした固定値を使う。
`divideBoundary` が 8 セルちょうどになる値にしてある。

フィクスチャの大きさが変わると全測定項目の絶対値も変わるので、
セル数と大きさを固定した値にして、変えた理由が分かるようにしている。

### CI での扱い

`deploy.yml` は `actions/cache` で `OSM_CACHE_DIR` を復元してから `fetch-fixture.mjs` を実行し、
キャッシュがヒットしなかったときだけ保存する。

キャッシュ key は固定なので、取得した OSM データはそのまま使い回される。
base と head は同じ復元キャッシュを見るので、比較する 2 つの計測は同一のグラフに対する値になる。

キャッシュが退避されて取り直すときだけ、その時点の OSM データになって全測定項目がずれる。
それはグラフが変わった差なので、検出できる差のうちの 1 つとして扱う。

## 落とし穴

### pnpm check に bench を含める

`app/bench/**` は `pnpm check`（svelte-check）の対象外だった。
`jsconfig.json` の `include` が `.svelte-kit/tsconfig.json` の include（`src` / `tests` のみ）を使うため。

bench を型検査するには `bench/**/*.ts` を `include` に足す。

**include を自分で書くと `$env/dynamic/private` が 5 error になる。**
`.svelte-kit/ambient.d.ts` / `env.d.ts` / `non-ambient.d.ts` / `.svelte-kit/types/**/$types.d.ts` /
`vite.config.*` を失うため、列挙し直す必要がある。

### node と pnpm は nix develop 経由

flake.nix はリポジトリルートにある。
`app/` で実行すると `path does not contain a 'flake.nix'` が出る。
リポジトリルートから `pnpm -C app ...` とする。

### worktree ごとに pnpm install が必要

worktree を新規作成したら `pnpm install --frozen-lockfile` が要る。
node_modules は worktree 間で共有されない。

base 側の checkout も `--ignore-scripts` でインストールするため、
`svelte-kit sync` を明示的に実行する必要がある（bench が `.svelte-kit/tsconfig.json` を参照するため）。

### pnpm lint は 29 errors のまま

bench 変更前から 29 errors のままで、CI も `pnpm lint` を走らせない。
