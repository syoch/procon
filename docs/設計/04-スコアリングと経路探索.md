# スコアリングと経路探索

## スコア軸

各エッジに以下の 3 軸スコアを計算し、重み付き和を総合スコアとする。

| 軸 | 算出方法 | データソース |
|----|----------|-------------|
| 幅員 | 道路の広さ（狭さは幅員スコアで表現） | `highway`, `width`, `sidewalk` タグ |
| 視界 | 曲率 | `group_nodes` 座標列、（進入エッジ, 退出エッジ）ペア |
| 混在 | 歩行者・自転車との分離度 | `highway` 種別、`sidewalk` タグ、`width` |

## 総合スコア

```
総合スコア = α₁ × 幅員 + α₂ × 視界 + α₃ × 混在
```

## エッジコスト

```
cost = 距離 × (1 + λ × (1 - 総合スコア))
```

## CalculateCost

`FoldedEdge` の `segments[]` を反復し、各セグメントの属性で個別にスコアを算出・合算する。`group_nodes` からエッジ内部曲率（視界スコア）を計算する。出力は `ComputedEdge`。

## 交差点曲率計算

交差点における曲率計算（turn score）は、エッジスコアとは独立に計算する。

| 項目 | 説明 |
|------|------|
| 計算場所 | `cross_transform.js` の `calculateViewScore()`。グラフ構築時に `MapVCrossEdge.view_score` として**一度だけ**計算して焼き込む |
| 入力 | 進入側の隣接ノード座標、交差点座標、退出側の隣接ノード座標 |
| 計算 | 進入方向 (begin → intersection) と退出方向 (intersection → end) のなす回頭角 θ を π で正規化し `score = 1 - θ/π` |
| 読み出し | `path_finder.ts` の `calculateEdgeCost` が `MapVCrossEdge.view_score` をそのまま使う |
| コスト反映 | 回頭角度が大きいほど視界スコアが低下（走りづらい） |

基準値:

| 形状 | `turn_score` |
|---|---|
| 直進 | 1.0 |
| 45° | 0.75 |
| 90° | 0.5 |
| U ターン | 0.0 |
| 座標が縮退して角度を求められない | 1.0 |

座標縮退時に 1.0 を返すのは「判定できない＝危険猜测しない」という方針。
直進と同じ扱いなので、判定不能な交差点を回避する動機は生まれない。

コスト式（巡回時）:

```
turn_cost = 距離 × (1 + λ × (1 - turn_score))
          ただし turn_score は回頭曲率から求めた視界スコア（0–1）
```

エッジ内部曲率と SCC 回頭曲率は以下のように分担する:

```
FoldedEdge A ──→ SCC ──→ FoldedEdge B

A の視界スコア = A.group_nodes から計算（エッジ内部曲率）
B の視界スコア = B.group_nodes から計算（エッジ内部曲率）
SCC 通過の視界スコア = (A の終点ベアリング, B の始点ベアリング) から計算

経路全体の視界スコア = A.視界 + SCC.視界 + B.視界
```

### 実装と設計の既知のずれ
座標縮退時に 1.0 を返すのは「判定できないものを危険と見なさない」という方針。
交差点内の幅員・混在は `ComputedEdge` にしか無く、`MapVCrossEdge` の型に
`width_score` / `mix_score` は存在しない。交差点のコストは
`MapVCrossEdge` の場合、視界のみが 1 軸で効いている。

また交差点内の距離は `calculateEdgeLength` を使わず **10 に固定**されている
（`path_finder.ts`）。上の `turn_cost = 距離 × ...` の「距離」が何を指すのか、
現時点では実装と設計が噛み合っていない。

このずれの解消（幅員・混在を交差点にも与えるか、turn score を独立軸にするか、
重み λ と各軸の重みをどう置くか）は未決。

**参照 Issue: スコアリングの見直し。**

## スコアの向き

3 軸のスコアはいずれも 0〜1 で「高いほど安全」。混在スコアは名前に反して「分離度」で、歩行者・自転車と分離されているほど高い（高速道路 1.0、両側歩道 0.8、歩道なし 0.3）。そのため重み付きで足し合わせ、総合スコアが高いほどコストが下がる。

## モードごとのスコア

移動モード（`mode` 指定時）は、幅員スコアと混在スコアの中身をモードごとに変える（`lib/mode_scoring.ts` の `SCORING_PROFILES`、`CalculateCost` の第 2 引数）。モードの定義が無い場合（`mode` なしの API）は従来の計算のまま。

背景:
- 以前の混在スコア（`calculateMixScore`）は、歩行者・自転車にとって最も安全な歩行者専用の道（footway / cycleway / path / steps）を 0.1（最も危険）と評価していた（switch に無い種別の default 分岐に落ちるため）。徒歩・自転車では評価が逆になる
- タグが無い道では幅員スコアも混在スコアも `highway` 種別から推定しており、両者は相関が強かった（どちらも幹線ほど高い）。徒歩で重みを幅員だけ・混在だけにしても、長岡駅→見附駅で同じ経路になった（値そのものは 15 種のうち 12 種で異なる）

### 幅員スコア（幅が分かる道）

国土地理院の幅員区分（約 9 割の区間で分かる）を使う。境目は幅員区分と道路構造令の車線の幅に合わせる。幅が分からない道は従来どおり `highway` 種別から推定する。

| 幅 | 車・バイク | 大型トラック | 意味 |
|----|-----------|-------------|------|
| 3m 未満 | 0.1 | 0.1 | 1 台通るのがやっと |
| 3〜5.5m | 0.4 | 0.2 | 1 車線の道路（標準 4m）。すれ違いが難しい |
| 5.5〜13m | 0.8 | 0.7 | 2 車線（車線の幅 3.0〜3.25m） |
| 13m 以上 | 1.0 | 1.0 | 多車線 |

徒歩・自転車は車道の幅より車との分離が大事なので、幅員スコアは従来どおりとし、重みを小さくする（0.2）。

### 混在スコア（幅が分かる道）

幅が分かる道は「幅員クラス × 歩道の有無」で決める。
幅は国土地理院の幅員（`width`）で、約 9 割の区間が分かる。
幅の境目は 3.0m / 5.5m（車両制限令 第 5 条・第 6 条の対面通行 5.5m・一方通行 3.0m）とする。
歩道の有無は `sidewalk` タグで見る（`none` / `no` 以外を歩道ありとする）。

| 幅員 | 歩道 | 徒歩 | 自転車 | 車・バイク・トラック |
|------|------|------|--------|---------------------|
| 3m 未満 | なし | 0.4 | 0.7 | 0.3 |
| 3m 未満 | あり | 0.6 | 0.7 | 0.6 |
| 3〜5.5m | なし | 0.5 | 0.6 | 0.5 |
| 3〜5.5m | あり | 0.6 | 0.6 | 0.7 |
| 5.5m 以上 | なし | 0.7 | 0.3 | 0.8 |
| 5.5m 以上 | あり | 0.8 | 0.4 | 0.8 |

- 徒歩・車系は幅が広い道ほど高い（歩道が整っている道が多い）
- 自転車は幅が広い道ほど低い（車が速い）
- 幅員クラスは幅員スコア（3m / 5.5m / 13m）とは別軸で、混在は混在の境目（3.0m / 5.5m）を使う

幅員クラスの値は統計ではなく、次の原理から決める。
- 幅が広い道ほど歩道が整っている（歩行者・自転車と分離されている）
- 狭い道ほど車が遅い（自転車には比較的安全）
- 歩道が無い道の値は、下の `highway` 種別の表の同じ種別の値にそろえる
- 歩道がある道は、歩道が無い道より高くする（両側歩道 0.8 など）

### 混在スコア（幅が分からない道）

`sidewalk` タグは付与率が延長の約 0.5% しかないため、主に `highway` 種別から推定する。`sidewalk` タグがある道は従来どおりそちらを使う。車系は従来どおり（歩行者・自転車から分かれているほど高い）。

| highway | 徒歩（車から） | 自転車（速い車から） |
|---------|---------------|-------------------|
| footway / pedestrian / path | 1.0 | 0.8 |
| steps | 1.0 | （通れない） |
| cycleway | 0.6 | 1.0 |
| residential / living_street | 0.6 | 0.7 |
| unclassified / service / track | 0.5 | 0.6 |
| tertiary | 0.5 | 0.4 |
| secondary / primary / trunk | 0.7（歩道があることが多い） | 0.3（車が速い） |
| その他 | 0.3 | 0.3 |

`highway` 種別の値も統計ではなく、種別ごとの分離の度合いを順序付けたものである。

### 経路差の実測（2026-10-04）

検証手段は `pnpm bench:modes` で、[`app/bench/README.md`](../../app/bench/README.md) の「モードごとの経路差の比較」に使い方と置く。
同じ始点・終点で 5 モードを探索し、経路が使う OSM の way の集合をモード間で突き合わせる。
一致率は「短い方の経路が何割共通しているか」で、100% が同じ経路を表す。
経路探索は本番と同じく、経路の周りの国土地理院タイルを足しながら `MAX_GSI_PASSES` 回までやり直す。

### 幅員クラスの混在スコアの効果（2026-10-07）

`mix_score` に幅員クラスを足す前後（`origin/main` と本変更）を、同じ始点・終点・幅員データで測った。

| モード | 距離 base [m] | 距離 head [m] | way 数 | 交差点数 | 幅員網羅率 | 経路 |
|--------|--------------|--------------|--------|---------|-----------|------|
| 徒歩 | 5071 | 5060 | 86 → 85 | 85 → 84 | 100.0% | 変わる |
| 自転車 | 5094 | 5094 | 81 | 80 | 100.0% | 同じ |
| 車 | 5152 | 5152 | 71 | 70 | 100.0% | 同じ |
| バイク | 5152 | 5152 | 71 | 70 | 100.0% | 同じ |
| 大型トラック | 5080 | 5080 | 13 | 12 | 100.0% | 同じ |

差が出たのは徒歩だけで、効いたスコアは次のとおり。
- 幅員 8m の `unclassified` は 0.5（`highway` 種別）から 0.7（5.5m 以上のクラス）に上がった
- そのため短い `unclassified` の経路が選ばれ、距離が 11m 短くなった

自転車は最初、3〜5.5m のクラスを 0.5 にしていたため住宅地 4m を避けて幹線に回る差が出た。
3〜5.5m を `unclassified` の 0.6 に合わせたところ、経路は base と一致した。

### 実測から判断したこと

**重みではなくスコアの中身が経路を分けている。**
徒歩と自転車の重みは同じで、`app/tests/mode-scoring/mode-scoring.test.ts` がその一致を保証している。
この 2 つは 7 組中 6 組で経路が違い、上の例では一致率 64.2% まで下がる。
つまり重みをそろえたあとも経路差は残る、という #85 の狙い通りである。

**バイクが車と同じ経路になるのは、重みの差が小さいためである。**
`SCORING_PROFILES` は車とバイクに同じ幅員スコアの段を割り当てている。
すれ違う相手はどちらも同じなので、スコアの中身が最初から同じになる。
残る差は重みだけで、7 組中 6 組では選択が返らず同じ経路になった。
附属病院→長岡駅東の 1 組では重みだけで経路が変わり、一致率は 61.1% になった。
バイクは車線に沿って走るはずだが、車線タグを使う処理が無いので現時点では出ない。
車線の扱いはスコアの中身の外にあるので、#85 の検証結果としてはこの差で足りる。

**大型トラックが経路を最も大きく変えるのは幅の下限が効いているためである。**
対面通行 5.5m / 一方通行 3.0m より狭い区間が 2114〜3885 区間が取り除かれ、探索グラフの辺数が 11195 から 4523〜7145 に減る。
始点・終点が狭い道だと `MAX_SNAP_DISTANCE_M` の判定で吸着に失敗するが、
本番の `doPathFind` も `removeNarrowEdges` の後に吸着の判定を通すので同じ挙動になる。

**値の根拠は幅員クラスで原理から与えた。**
実測が示しているのは「軸がモードを分けている」ことまでである。
幅員スコアの境目（3m / 5.5m / 13m）は道路構造令と国土地理院の区分から引いた。
混在スコアの幅員クラスは、幅が広いほど分離されているという原理と `highway` 種別の表との整合で決めた。
0.1 / 0.4 / 0.8 / 1.0 という点数と重み 0.1〜0.6 は統計が無く、順序だけを定めたものである。
点の妥当性を確かめるには統計（事故の多さ・実測の速度分布など）が要る。

## 距離

エッジの距離は `segments[]` の区間長の合計（`utils/haversine.ts` の `distanceOf`）。交差点の仮想エッジ（`MapVCrossEdge`）は 10m とする。

移動モードによっては、`highway` 種別ごとの倍率を区間長に掛けてから合計する（`PathFindOptions.highwayCostFactor`）。幅が分からない track / service を割高にし、抜け道に使わないためのもの。詳細は「06-移動モードと急カーブ」を参照。
